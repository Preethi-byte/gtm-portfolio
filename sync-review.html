CRM write-back and retry

When a provider sends an update twice or Salesforce is briefly unavailable, the workflow should leave a clear record of what happened. This browser simulation uses fictional events and runs without a CRM connection.

Integration replay

Run the sample batch, retry the failed record, then replay the batch to check for duplicate writes.

EventDecisionReason

Execution order

  1. Check the destination field against the enrichment allowlist. Block operational fields.
  2. Check whether the event ID already succeeded. Skip completed events.
  3. For a simulated temporary failure, retain the event in the pending queue.
  4. On success, remove it from pending, record its ID, and increment the simulated write count.

Expected trace: EV-101 applies; EV-102 is blocked; EV-103 waits for retry. Retry applies EV-103. Replay then skips EV-101 and EV-103, while EV-102 remains blocked.

Salesforce implementation boundary: Flow could use Decisions and a persistent event-log object. This demo has neither a live connection nor durable storage; production concurrency and lost acknowledgments need additional design.

Controls this demonstrates

Apply an allowlist for enrichment fields, use event IDs to avoid a second successful write, and keep failed events eligible for a retry. A production version would persist event IDs and audit records, use a durable queue, and apply CRM-side idempotency to handle a write that succeeds before acknowledgment.

The replay tracks successful event IDs and retryable failures in memory for this session.
