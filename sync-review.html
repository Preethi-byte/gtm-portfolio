CRM write-back and retry

When a provider sends an update twice or Salesforce is briefly unavailable, the workflow should leave a clear record of what happened. This browser simulation uses fictional events and runs without a CRM connection.

Integration replay

Run the sample batch, retry the failed record, then replay the batch to check for duplicate writes.

Controls this demonstrates

Apply an allowlist for enrichment fields, use event IDs to avoid a second successful write, and keep failed events eligible for a retry. A production version would persist event IDs and audit records, use a durable queue, and apply CRM-side idempotency to handle a write that succeeds before acknowledgment.

The replay tracks successful event IDs and retryable failures in memory for this session.
