THE OPERATING PROBLEM

A forecast meeting should start with questions worth answering.

A past close date, missing deal value, or silent activity history tells the reviewer what to investigate. None of those signals alone establishes buyer intent, forecast accuracy, or the probability of winning.

Rules implemented in the browser prototype
InputDecision ruleOwner action
Close dateEarlier than the fixed reference dateConfirm buyer timing before proposing a replacement date.
Last recorded activityMissing, or at least 21 days before the reference dateCheck whether buyer contact occurred and whether the next step is recorded.

The sample uses 17 November 2026 as a fixed reference so results remain reproducible. The 21-day threshold is an illustrative policy. A production policy needs agreement by segment, sales cycle, and activity coverage.

PROPOSED SALESFORCE IMPLEMENTATION

Keep the evidence and ownership in the CRM.

This design uses a review record for each opportunity and rule, rather than creating another task every time the daily check runs.

Salesforce opportunityRead deal value, close date, owner, stage, and the agreed activity source.
Evaluation processRun agreed checks daily. Re-evaluate relevant record changes where needed.
Persistent review recordStore the rule, evidence snapshot, status, assigned reviewer, and evaluation time.
Deal ownerVerify evidence and record a disposition. Commercial field changes follow existing permissions and approval rules.
Illustrative review-record schema
FieldPurpose
Opportunity__cLink the review to its source record.
Review_Key__cUnique external ID combining opportunity ID and rule code. Update the existing review instead of duplicating it.
Rule_Code__c, Rule_Version__cIdentify the policy and version that produced the flag.
Evidence__c, Evaluated_At__cPreserve the source values and evaluation timestamp.
Status__c, Disposition__cTrack open, acknowledged, and resolved reviews with an owner’s explanation.
OwnerIdAssign an accountable reviewer with fallback handling for inactive owners.
Implementation choice: Flow or Apex?

Start with scheduled Flow for a small, bounded pilot using simple rules. Validate query volume, execution limits, update behaviour, and concurrent runs in a sandbox. Use a bulk-safe Apex service and upsert by review key if atomic deduplication, larger workloads, or more complex policy evaluation require it. Document the reason for the choice before rollout.

Implementation choice: activity evidence

Agree which activities count as meaningful buyer engagement. Confirm that the chosen Salesforce field or related activity source includes the team’s actual capture tools. Missing captured activity must remain “no recorded activity”; it must not become “no buyer engagement.”

Implementation choice: reviewed versus resolved

Acknowledging a review records that someone inspected it. Resolve a flag only when the source data clears the rule or an authorized disposition explains the exception. Keep repeat evaluations and owner actions in review history.

EXCEPTIONS & CONTROL

Design for the cases that break the happy path.

Failure or exceptionProposed response
A daily job encounters an existing flagUpdate by unique review key. Notify on a new or materially changed flag, not every evaluation.
The job fails partway through a batchLog record-level failures, retain successful results, and reprocess failures using the same keys.
The opportunity closes or is correctedRe-evaluate and resolve obsolete flags. Retain history.
The owner is inactive or inaccessibleRoute to an agreed RevOps fallback and log the ownership exception.
The activity feed is incompleteShow the evidence limitation and ask for verification.
A rule creates too many low-value flagsReview owner dispositions, adjust the versioned policy, and measure useful-action rate.
A reviewer lacks record accessRespect sharing and field access. Do not expose opportunity data through notifications or external pages.

ROLLOUT & SUCCESS CRITERIA

Prove usefulness before expanding the automation.

  1. Agree the policy. Choose a segment, activity source, reviewer, thresholds, and exceptions with Sales and RevOps.
  2. Validate in a sandbox. Exercise boundary dates, missing values, repeat runs, ownership changes, and partial failures.
  3. Run a bounded pilot. Collect owner dispositions before adding notifications or broadening access.
  4. Review the evidence. Measure review preparation time, duplicate-review rate, owner response time, and the proportion of flags leading to a confirmed action.

No percentage improvement is claimed. Capture a baseline and agree a target with the process owner before evaluating impact.
